# Lecture 10 — GitHub Projects: доска задач и рабочий процесс проекта

> Эта запись — общая организационная лекция для участников разных языковых направлений. Синтаксис TypeScript в ней не рассматривается. Основная тема — работа с GitHub Projects, User Stories, тест-кейсами, задачами и Pull Request.

## Краткая выжимка

- Доска делает работу команды видимой: что запланировано, что выполняется, что проверяется и что завершено.
- Карточка проходит по статусам `Todo` → `In Progress` → `Review` → `Done`.
- `User Story` описывает потребность пользователя и ожидаемый результат; инженеры получают готовые User Stories и не создают собственные.
- Из одной User Story могут появиться несколько инженерных задач и тест-кейсов.
- Карточка задачи и Pull Request должны быть связаны в обе стороны.
- Неавтоматизированный тест-кейс можно вынести на отдельное ревью, а затем завершить либо передать на автоматизацию.
- Если в процессе работы обнаружена отдельная ошибка, для нее создается самостоятельная карточка, чтобы проблема не потерялась.
- User Stories на учебной доске общие: любой участник может создавать к ним тесты.
- Жестких сроков и обязательного минимального числа тестов лектор не устанавливает; ценность дает практическая работа с доской.
- ИИ разрешено использовать для подготовки текста, но результат обязательно нужно прочитать и проверить.

## 1. Зачем нужна доска задач

Доска показывает состояние проекта всей команде. В классическом варианте работа представлена карточками, которые перемещаются между колонками:

| Колонка | Смысл |
|---|---|
| `Todo` | задачу еще предстоит выполнить |
| `In Progress` | исполнитель взял задачу и работает над ней |
| `Done` | работа завершена |

Лектор начинает с физической доски с бумажными карточками. Исполнитель берет карточку, тем самым принимает ответственность за задачу, и переносит ее по мере выполнения. В GitHub Projects используется тот же принцип, но в электронном виде.

Главная польза — прозрачность: руководитель и участники видят, сколько работы запланировано, кто чем занят и что уже закончено.

**Простой пример.** Карточка «Проверить создание папки» находится в `Todo`. Инженер назначает себя исполнителем и переносит ее в `In Progress`. После завершения карточка попадает в `Done`.

**Пример среднего уровня.** Во время выполнения выяснилось, что задача зависит от чужой работы. Карточку можно вернуть назад или отметить как заблокированную; лектор подчеркивает, что на реальной доске статусов может быть больше трех.

> **В лекции изложено невнятно.** Лектор связывает происхождение досок одновременно со Scrum и Agile и сам оговаривается, что может быть неточен в исторических деталях.

> **Дополнения от AI.** Для практической работы достаточно разделять понятия так: Agile — набор принципов гибкой разработки; Scrum — один из способов организации работы короткими периодами; визуальная доска — отдельный инструмент, который может применяться и в Scrum, и вне его.

## 2. Scrum-практики, упомянутые в лекции

Лектор кратко описывает несколько практик:

- работа делится на короткие периоды — спринты, часто примерно по две недели;
- каждый день проводится короткий stand-up;
- на stand-up участник отвечает на три вопроса:
  1. Что я сделал вчера?
  2. Что я буду делать сегодня?
  3. Есть ли у меня препятствия?
- встречу проводят стоя, чтобы она оставалась короткой;
- полезные практики могут применяться отдельно от полного Scrum-процесса.

**Простой пример.** «Вчера создала тест-кейс. Сегодня автоматизирую его. Препятствий нет».

**Пример среднего уровня.** «Вчера начала автоматизацию. Сегодня планировала создать Pull Request, но не могу продолжить: нужное изменение другого участника еще не объединено». Это сообщает команде о блокировке.

## 3. Карточка в GitHub Projects

Карточка содержит описание конкретной единицы работы. На демонстрации лектор показывает, что в ней можно указать:

- название;
- подробное описание;
- исполнителя (`Assignee`);
- метки (`Labels`);
- дополнительные поля, например приоритет;
- комментарии и историю действий.

Карточку можно назначить себе, перенести в другой статус и при необходимости вернуть назад. В комментариях участники обсуждают работу и проводят ревью текста тест-кейса.

**Простой пример.** Название карточки: «Проверить создание нового элемента». В описании перечислены действия и ожидаемый результат.

**Пример среднего уровня.** В карточке указан исполнитель, метка тест-кейса, связь с User Story и ссылка на Pull Request. По истории карточки видно, кто менял статус и какие замечания были оставлены.

## 4. Структура доски, показанная лектором

На доске используются следующие колонки:

| Колонка | Как ее описывает лектор |
|---|---|
| `Templates` | шаблоны карточек; шаблон копируют и затем изменяют |
| `User Stories` | утвержденные пользовательские истории; инженеры их читают и используют как основу |
| `Todo` | доступные задачи, которые еще не взяли в работу |
| `In Progress` | задачи, над которыми сейчас работают |
| `Review` | работа подготовлена и ожидает проверки; Pull Request еще не объединен |
| `Done` | завершенная работа; для связанного Pull Request переход может произойти автоматически после объединения |

**Простой пример.** Инженер копирует шаблон, заполняет карточку и помещает ее в `Todo`.

**Пример среднего уровня.** Инженер берет свободную карточку из `Todo`, назначает себя, переносит ее в `In Progress`, создает Pull Request и переводит карточку в `Review`. После объединения Pull Request карточка оказывается в `Done`.

## 5. User Story

User Story описывает функцию с точки зрения конечного пользователя. Лектор приводит общую форму:

> Как пользователь, я хочу получить некоторую возможность, чтобы достичь определенной цели.

В User Story также могут находиться пояснение причины и критерии приемки — условия, по которым проверяют, что функция работает ожидаемым образом.

Одна User Story может породить несколько конкретных задач. Например, общая возможность создания сущности может требовать отдельных проверок для папки, freestyle-проекта и pipeline.

**Простой пример.** «Как пользователь, я хочу создать новый элемент, чтобы использовать его в дальнейшей работе».

**Пример среднего уровня.** Для одной User Story создаются отдельные карточки: позитивная проверка создания, проверка обязательных полей и проверка поведения при некорректном вводе.

> **В лекции изложено неполно.** Лектор объясняет назначение User Story и упоминает критерии приемки, но не задает обязательный шаблон описания для текущего проекта.

> **Дополнения от AI.** При работе с этой доской не нужно самостоятельно расширять формат User Story. Следует скопировать утвержденные заголовок и описание из исходной доски, как требует лектор, а возникающие вопросы вынести в общий чат.

## 6. Связь User Story, задачи и Pull Request

Лектор показывает цепочку прослеживаемости:

`User Story` → инженерная задача или тест-кейс → `Pull Request`

Карточка конкретной работы связывается с родительской User Story. После написания кода к карточке прикрепляется Pull Request. Лектор называет карточку центром рабочего процесса: из нее должно быть можно перейти к коду, а из Pull Request — вернуться к карточке.

**Простой пример.** В карточке теста размещена ссылка на User Story, из которой появился этот тест.

**Пример среднего уровня.** Reviewer получает ссылку на карточку, читает исходную User Story, проверяет шаги теста и переходит в связанный Pull Request. Если отправлена ссылка на Pull Request, из него также должна открываться карточка.

## 7. Тест-кейс и автоматизация

Тест-кейс может существовать отдельно от автоматизации. По описанному процессу участник может:

1. создать карточку тест-кейса;
2. записать в ней шаги;
3. перенести карточку в `Review`;
4. попросить других участников проверить именно тест-кейс, а не Pull Request;
5. после одобрения либо завершить работу, либо передать карточку на автоматизацию.

Один человек может написать тест-кейс и автоматизировать его. Также эти этапы могут выполнить разные люди. Допустимо сразу заниматься автоматизацией без отдельного формального тест-кейса, но карточка должна достаточно ясно объяснять, что проверяется, чтобы reviewer понял Pull Request.

На показанной доске видны метки `TC` и `AT`. В речи лектор противопоставляет обычный тест-кейс и автоматизированный тест.

**Простой пример.** Участник описывает ручную проверку, получает комментарий reviewer и после исправления переводит карточку в `Done`.

**Пример среднего уровня.** После ревью ручного тест-кейса автор меняет назначение карточки на автоматизацию, переносит ее в `Todo`. Другой участник берет карточку, назначает себя и переводит в `In Progress`.

> **В лекции изложено невнятно.** Названия меток произносятся нечетко; на экране видны сокращения `TC` и `AT`, но лектор не дает им отдельного строгого определения. Также не закреплен единственный обязательный маршрут карточки после ревью тест-кейса.

> **Дополнения от AI.** По показанному процессу удобно читать `TC` как карточку тест-кейса, а `AT` — как карточку автоматизированного теста. Однако перед массовым созданием карточек следует проверить актуальные значения меток в правилах вашей доски или уточнить их у ответственного преподавателя.

## 8. Что делать с обнаруженной ошибкой

Если во время работы или проверки Pull Request упал тест, который не относится к текущему изменению, лектор предлагает:

- не смешивать постороннюю проблему с текущей работой;
- создать отдельную карточку ошибки;
- приложить сведения о падении или лог;
- поместить карточку в `Todo`, чтобы проблема не потерялась;
- при необходимости уведомить автора связанного кода.

**Простой пример.** При запуске набора тестов упал старый несвязанный тест. Создается отдельная карточка с названием сбоя и логом.

**Пример среднего уровня.** Reviewer продолжает оценивать текущий Pull Request по его назначению, а для побочной ошибки заводит отдельную карточку, связывает ее с контекстом обнаружения и сообщает участнику, который сможет ее исследовать.

## 9. Общие User Stories и правила копирования

Для текущего потока User Stories берутся с публичной доски предыдущего потока. Правила лектора:

- у студентов исходная доска доступна только для чтения;
- в новую доску копируются заголовок и описание;
- на копию ставится метка User Story;
- переносить карточку целиком не следует, потому что тогда она исчезнет с исходной доски;
- дополнительные связи и поля старой доски копировать не требуется;
- собственные User Stories, которых нет среди утвержденных, создавать не нужно;
- все скопированные User Stories общие, а не принадлежат человеку или группе, которая их перенесла;
- если появились дубликаты, лишнюю копию можно удалить.

Лектор просит участников переносить по одной или несколько историй, а не копировать сразу слишком много.

**Простой пример.** Участник выбирает утвержденную User Story, копирует ее название и описание на новую доску и добавляет соответствующую метку.

**Пример среднего уровня.** Один участник перенес User Story, а несколько других создали для нее разные тест-кейсы. История остается общей; переносивший ее участник не получает исключительных прав на работу с ней.

## 10. Повторяющиеся тесты

В учебном проекте лектор разрешает создавать одинаковые или похожие тесты. Позже команда сможет потренироваться удалять дубликаты. При совпадении имен предлагается использовать нумерацию классов или модулей.

При этом лектор просит по возможности разнообразить работу: если весь поток будет создавать одинаковые тесты для одной истории, учебная ценность снизится.

**Простой пример.** Уже существует класс `FolderTest`; второй участник создает `FolderTest1` со своей реализацией аналогичной проверки.

**Пример среднего уровня.** Два участника автоматизируют один сценарий разными способами, после чего команда сравнивает варианты и позднее очищает проект от повторов.

## 11. Роли участников и управление доской

В предыдущем процессе User Stories готовили бизнес-аналитики или product managers, а инженеры создавали конкретные задачи. В текущем потоке отдельной группы для этой роли нет, поэтому участники совместно поддерживают порядок на доске.

Инженер может:

- создавать карточки задач для себя или других;
- создавать карточки ошибок и рефакторинга;
- брать неназначенную работу из `Todo`;
- при желании копировать утвержденные User Stories;
- участвовать в обсуждении и ревью.

Лектор планирует назначить нескольких ответственных участников с расширенными правами. Точный порядок выдачи доступа во время лекции еще не был окончательно установлен. Для разных языковых направлений детали могут различаться; для JavaScript/TypeScript их должен дополнительно объяснить Борис.

**Простой пример.** Инженер видит свободную карточку в `Todo`, назначает себя и начинает работу.

**Пример среднего уровня.** Ответственный за доску замечает, что не хватает нужной метки или поля, обсуждает это с преподавателем и помогает привести карточки к общему формату.

> **В лекции изложено неполно.** Не определены окончательный список администраторов, способ подачи заявки и все различия между языковыми направлениями.

> **Дополнения от AI.** До отдельного объявления не следует предполагать наличие расширенных прав. Обычный участник может работать с доступными карточками, а вопросы о недостающих метках, полях и разрешениях направлять ответственному за свое направление.

## 12. Темп работы и практическая цель

Лектор не устанавливает дедлайн вида «за неделю команда обязана сделать десять тест-кейсов». Каждый работает в своем темпе с учетом занятости.

При этом он рекомендует получить как можно больше практики: создавать карточки, писать тесты, переносить задачи, изучать настройки доски. По его мнению, реальный опыт заметен на собеседовании лучше, чем знание одной теории.

**Простой пример.** Участник создает одну качественно оформленную карточку и проводит ее через весь процесс.

**Пример среднего уровня.** Участник переносит User Story, готовит несколько разных тест-кейсов, участвует в ревью чужой карточки и связывает собственную автоматизацию с Pull Request.

## 13. Коммуникация и спорные ситуации

Если User Story непонятна, вопрос нужно вынести в общий чат: дать ссылку, назвать неясное место и попросить пояснение. Вопросы о доске, тест-кейсах и процессе также обсуждаются в канале соответствующего языкового направления.

Если участники не могут решить конфликт самостоятельно, лектор предлагает отметить его в соответствующем канале и описать ситуацию, чтобы обсудить решение.

**Простой пример.** «В этой User Story неясен ожидаемый результат третьего шага. Подскажите, как его понимать?»

**Пример среднего уровня.** Два участника по-разному понимают границы теста. Они прикладывают ссылку на карточку, описывают оба варианта и просят преподавателя разрешить спор.

## 14. Использование ИИ

Лектор разрешает использовать ИИ при написании тест-кейсов и других текстов. Однако сгенерированный материал необходимо самостоятельно прочитать и проверить: он должен быть адекватным, понятным и соответствовать задаче.

**Простой пример.** ИИ предлагает черновик шагов тест-кейса, а участник сверяет его с User Story и исправляет несоответствия.

**Пример среднего уровня.** ИИ помогает сократить длинное описание задачи, но инженер проверяет, что в краткой версии не потеряны условия и критерии приемки, прежде чем использовать ее в работе.

## Чек-лист работы с новой задачей

1. Найти утвержденную User Story.
2. Понять, какую конкретную проверку или задачу нужно выполнить.
3. Создать или взять карточку в `Todo`.
4. Проверить заголовок, описание, метку и связи.
5. Назначить себя исполнителем.
6. Перевести карточку в `In Progress`.
7. Выполнить работу и создать Pull Request, если был написан код.
8. Связать карточку и Pull Request.
9. Перевести работу в `Review` и запросить проверку.
10. Учесть замечания.
11. После завершения перевести карточку в `Done` либо дождаться автоматического перехода после объединения Pull Request.

# Вопросы и ответы

## 1. Для чего нужна доска GitHub Projects?

Чтобы сделать работу команды прозрачной: видеть задачи, их исполнителей и текущий статус.

## 2. Какие основные статусы проходит карточка?

`Todo` → `In Progress` → `Review` → `Done`. На реальном проекте могут быть и дополнительные состояния, например блокировка.

## 3. Что означает `Todo`?

Это задачи, которые еще не взяты в работу. Инженер может выбрать неназначенную карточку и назначить себя.

## 4. Что находится в `Review`?

Работа, подготовленная к проверке: например, карточка с Pull Request, который еще не объединен, или тест-кейс, ожидающий содержательного ревью.

## 5. Должны ли инженеры текущего потока писать собственные User Stories?

Нет. Лектор требует использовать утвержденные User Stories с исходной публичной доски и не создавать новые истории самостоятельно.

## 6. Кому принадлежат скопированные User Stories?

Они общие. Любой участник может создать тест-кейс для любой User Story независимо от того, кто перенес ее на доску.

## 7. Почему User Story нужно копировать, а не переносить?

Лектор хочет сохранить оригинальные карточки на исходной доске для будущих потоков. Перенос мог бы удалить карточку из источника.

## 8. Может ли один человек написать тест-кейс, а другой автоматизировать его?

Да. Также один участник может выполнить оба этапа.

## 9. Обязательно ли сначала создавать отдельный ручной тест-кейс?

Нет. Лектор разрешает сразу заниматься автоматизацией, но карточка должна достаточно понятно описывать проверку для reviewer.

## 10. Что делать, если во время проверки упал несвязанный тест?

Создать отдельную карточку ошибки, приложить сведения о падении и оставить ее в `Todo`, чтобы проблема не потерялась.

## 11. Должны ли карточка и Pull Request быть связаны?

Да. Из карточки должен открываться Pull Request, а из Pull Request — соответствующая карточка.

## 12. Разрешены ли одинаковые тесты?

На данном учебном этапе — да. Лектор допускает дубликаты, хотя рекомендует разнообразить работу; позже возможна практика по их очистке.

## 13. Есть ли обязательный срок и минимальное количество тест-кейсов?

Нет. Участники работают в своем темпе, но лектор рекомендует получить как можно больше практического опыта.

## 14. Куда обращаться, если User Story непонятна?

В общий чат соответствующего направления: приложить ссылку на карточку и описать, что именно непонятно. Если вопрос не решается, можно отметить преподавателя.

## 15. Можно ли использовать ИИ для написания тест-кейсов?

Да, но результат необходимо самостоятельно прочитать и проверить на понятность, адекватность и соответствие задаче.
