# Часть 1. Принципы ООП

## 1. Что такое ООП

**ООП** — объектно-ориентированное программирование (object-oriented programming, OOP) — подход, при котором программа рассматривается как набор классов и их объектов, взаимодействующих друг с другом. Каждый объект имеет свои характеристики и своё поведение.

Чем это отличается от того, как писали раньше: код шёл строго сверху вниз, вторая строка зависела от первой, третья от второй. В ООП вы работаете с готовыми объектами — передаёте им аргументы и получаете результат.

Главное преимущество, которое подчеркнул лектор: **вам не обязательно знать, как объект устроен внутри**. Достаточно знать, что он существует, что ему передать и что он вернёт. Именно это делает возможными библиотеки и фреймворки — вы подключаете чужой код и пользуетесь им, не читая его.

ООП лежит в основе многих языков: TypeScript, Java, C# и других.

### Четыре принципа

| Принцип | О чём он |
|---|---|
| Наследование (inheritance) | создавать классы на основе других классов |
| Инкапсуляция (encapsulation) | класс сам решает, что показывать наружу |
| Абстракция (abstraction) | показывать только то, что нужно для задачи; скрывать «как» |
| Полиморфизм (polymorphism) | один и тот же метод работает по-разному в разных классах |

Говоря «мы используем ООП», имеют в виду, что в коде применяется один или несколько из этих принципов — не обязательно все сразу.

## 2. Наследование

### Задача, из которой это выросло

Описываем машину. Сначала всё в одном классе: имя, цвет, модель, год выпуска, страна производства и так далее. Проблемы начинаются быстро:

- свойств становится 15–20;
- часть свойств подходит одной модели и не подходит другой — приходится делать их опциональными;
- каждый объект собирается вручную, растёт шанс ошибки.

Решение — разбить один большой класс на несколько маленьких и связать их.

**Наследование** (inheritance) — возможность создавать классы на основе других классов. Есть класс-родитель (parent class; его также называют базовым — base class, или суперклассом — superclass) и класс-ребёнок (child class), он же дочерний или производный (derived class). Ребёнок получает все свойства и методы родителя и может добавить свои.

### Базовый синтаксис

```ts
class Родитель {
    constructor(public поле: Тип) {}
}

class Ребёнок extends Родитель {
    constructor(поле: Тип, public своёПоле: Тип) {
        super(поле);          // вызов конструктора родителя
    }
}
```

- `extends` — зарезервированное слово, связывает ребёнка с родителем;
- `super(...)` — вызывает конструктор родителя и передаёт туда то, что родитель ожидает.

Почему нельзя просто написать `this.name = name`: поле `name` создаётся не в этом классе, а в родительском. `super(name)` говорит «иди в конструктор родителя и сделай то, что он требует».

### Пример

```ts
class Car {
    constructor(public name: string) {}

    getName(): string {
        return this.name;
    }
}

class Color extends Car {
    constructor(name: string, public color: string) {
        super(name);
    }

    getColor(): string {
        return this.color;
    }
}

const colorCar = new Color("Toyota", "red");

console.log(colorCar.getColor());   // red    — свой метод
console.log(colorCar.getName());    // Toyota — метод родителя
console.log(colorCar);              // Color { name: 'Toyota', color: 'red' }
```

Обратите внимание: у объекта `colorCar` доступны **и** `getColor()`, и `getName()`, хотя `getName()` объявлен только в `Car`. Это и есть наследование в действии.

Проверка принадлежности работает в обе стороны:

```ts
console.log(colorCar instanceof Color);   // true
console.log(colorCar instanceof Car);     // true
```

### Несколько детей от одного родителя

```ts
class Model extends Car {
    constructor(name: string, public model: string) {
        super(name);
    }
    getModel(): string { return this.model; }
}
```

Теперь от `Car` наследуются два независимых класса — `Color` и `Model`. Оба видят содержимое `Car`, но **не видят друг друга**: `Color` ничего не знает про `Model` и наоборот.

### Цепочка наследования

Ребёнок сам может стать родителем:

```ts
class Type extends Model {
    constructor(name: string, model: string, public type: string) {
        super(name, model);
    }
    getType(): string { return this.type; }
}

const t = new Type("Toyota", "Corolla", "sedan");
console.log(t.getType());    // sedan     — своё
console.log(t.getModel());   // Corolla   — от Model
console.log(t.getName());    // Toyota    — от Car
```

`Type` видит всё: себя, `Model` и `Car`. Направление видимости — **только снизу вверх**: `Model` ничего не знает про `Type`, `Car` не знает ни про кого.

Обратите внимание на `super(name, model)` — в родителя передаётся столько аргументов, сколько он ожидает, через запятую, и **порядок важен**.

**Уточнение (в лекции не прозвучало).** `super(...)` должен быть вызван **до** первого обращения к `this` в конструкторе. Если переставить строки местами:

```ts
class Color extends Car {
    constructor(name: string, public color: string) {
        this.color = color;   // ошибка TS17009:
        super(name);          // 'super' must be called before accessing 'this'
    }                         // in the constructor of a derived class
}
```

Правило простое: `super(...)` — первая строка конструктора дочернего класса.

## 3. Правила наследования

1. **Дочерний класс может наследовать только от одного родителя.** От двух сразу — нельзя:

   ```ts
   class C extends A, B {}   // ошибка TS1174: Classes can only extend a single class
   ```

2. **От одного родителя может наследоваться сколько угодно детей.**
3. **Цепочку наследования можно продолжать** — ребёнок становится родителем следующего. Но чем длиннее цепочка, тем сложнее код.
4. **Если у родителя есть свойства в конструкторе**, ребёнок обязан передать их через `super(...)` перед тем, как работать со своими.
5. **Все методы и поля родителя переходят к ребёнку** автоматически.
6. **Порядок объявления классов в файле не важен.** На вопрос про hoisting лектор ответил верно: это не подъём функций, порядок роли не играет, главное — чтобы класс существовал. Больше того, родитель и ребёнок часто лежат в **разных файлах** и связываются через `import`/`export` из прошлой лекции.

### `super` нужен не всегда

Если у родителя нет конструктора с параметрами — `super(...)` не нужен. Если у ребёнка вообще нет конструктора, TypeScript подставит его сам.

Технически можно создать и полностью пустой дочерний класс:

```ts
class Model extends Car {}
```

Работать будет, но смысла нет: обычно у ребёнка есть собственные поля и методы, которых нет у родителя. Ради этого наследование и затевается.

## 4. Инкапсуляция

**Инкапсуляция** (encapsulation) — объект сам решает, какую информацию раскрывать внешнему миру, а какую нет. Реализуется через модификаторы доступа (access modifiers) `public` и `private` из прошлой лекции.

### Задача

Класс сотрудника с зарплатой:

```ts
class Employee {
    monthlyBonus: number = 1000;

    constructor(
        public name: string,
        public age: number,
        public baseSalary: number,
    ) {}

    calculateSalary(): number {
        return this.baseSalary + this.monthlyBonus;
    }

    getDetails(): string {
        return `${this.name}, ${this.age} years old, salary ${this.calculateSalary()}`;
    }
}
```

Две проблемы:

1. Снаружи виден метод `calculateSalary()` — то есть виден сам способ расчёта зарплаты.
2. Снаружи можно изменить бонус: `emp.monthlyBonus = 5000` — и зарплата вырастет. Бонус назначает компания, а не кто угодно снаружи.

### Решение

```ts
class Employee {
    private monthlyBonus: number = 1000;

    constructor(
        public name: string,
        public age: number,
        public baseSalary: number,
    ) {}

    private calculateSalary(): number {
        return this.baseSalary + this.monthlyBonus;
    }

    public getDetails(): string {
        return `${this.name}, ${this.age} years old, salary ${this.calculateSalary()}`;
    }
}

const emp = new Employee("John", 30, 2000);
console.log(emp.getDetails());   // John, 30 years old, salary 3000
```

Теперь наружу торчит только `getDetails()`. Как считается зарплата — не видно, изменить бонус снаружи нельзя.

На резонный вопрос из зала «но я же вижу расчёт прямо в коде на экране» лектор ответил по существу: вы видите его, **потому что пишете этот класс**. Тот, кто будет этим классом пользоваться — другая команда, другая компания, вы же сами через пять лет — увидит только публичную часть. Часто исходный код чужого класса вообще недоступен.

**Уточнение (повтор из лекции 8, но важно помнить).** `private` — конструкция TypeScript, проверка на этапе компиляции. В рантайме поле остаётся на месте:

```ts
console.log(emp);
// Employee { name: 'John', age: 30, baseSalary: 2000, monthlyBonus: 1000 }
```

Инкапсуляция в TypeScript защищает от ошибок разработчика, а не от доступа к данным.

## 5. Абстракция

**Абстракция** (abstraction) — класс предоставляет только ту информацию, которая нужна для конкретной задачи. Она отвечает на вопрос **что** делает объект, а не **как** он это делает.

### Задача

Приложение для рисования фигур: круги, квадраты, треугольники. Можно сделать один обычный класс и внутри каждого метода писать `if`: если квадрат — одно, если круг — другое. Проблема: добавляя новую фигуру, придётся возвращаться в этот класс и дописывать ещё один `if`. И так каждый раз.

Вместо этого делается **класс-шаблон**, который задаёт правила, а реализацию этих правил оставляет наследникам. Такой класс называется **абстрактным** (abstract class), а объявленный в нём метод без тела — **абстрактным методом** (abstract method).

### Базовый синтаксис

```ts
abstract class ИмяКласса {
    constructor(public поле: Тип) {}

    abstract имяМетода(): ТипРезультата;    // правило: тела нет, только подпись

    обычныйМетод(): void {
        // обычный метод с телом — разрешён
    }
}
```

- `abstract` перед `class` — это шаблон, создать объект от него нельзя;
- `abstract` перед методом — правило: метод обязан быть реализован в наследнике, **тела у него нет**;
- обычные методы (без `abstract`) в абстрактном классе разрешены и наследуются как обычно.

### Пример: шаблон фигуры

```ts
abstract class Shape {
    constructor(public color: string) {}

    abstract calculateArea(): number;

    describe(): void {
        console.log(`This is a ${this.color} shape with an area of ${this.calculateArea()}`);
    }
}
```

Два правила, которые задаёт этот шаблон: у каждой фигуры будет цвет, и каждая фигура обязана уметь считать свою площадь. **Как** считать — шаблону всё равно.

### Абстрактный класс нельзя инстанцировать

```ts
const s = new Shape("red");
// ошибка TS2511: Cannot create an instance of an abstract class
```

Это не обычный класс, который что-то делает. Это набор правил для будущих классов. Единственный способ его использовать — унаследовать.

«Инстанцировать» — то же, что «создать экземпляр класса» (instance; сам процесс — instantiation).

### Реализация в наследниках

```ts
class Circle extends Shape {
    constructor(color: string, private radius: number) {
        super(color);
    }

    calculateArea(): number {
        return Math.PI * this.radius ** 2;
    }
}

class Rectangle extends Shape {
    constructor(color: string, private width: number, private height: number) {
        super(color);
    }

    calculateArea(): number {
        return this.width * this.height;
    }
}

const circle = new Circle("red", 5);
const rect = new Rectangle("blue", 4, 6);

console.log(circle.calculateArea());   // 78.53981633974483
circle.describe();                     // This is a red shape with an area of 78.53981633974483
console.log(rect.calculateArea());     // 24
rect.describe();                       // This is a blue shape with an area of 24
```

Обратите внимание: `describe()` в обоих классах взялся из родителя — он обычный метод, его не нужно переписывать. А `calculateArea()` у каждого свой, потому что он был помечен `abstract`.

Радиус сделан `private` — это уже инкапсуляция. В одном примере работают три принципа сразу: наследование, инкапсуляция и абстракция. Именно так ООП и применяется.

### Что будет, если правило не выполнить

```ts
class Circle extends Shape {
    constructor(private radius: number) { super(); }
    // calculateArea не реализован
}
// ошибка TS2515: Non-abstract class 'Circle' does not implement
// inherited abstract member calculateArea from class 'Shape'
```

Наследник **обязан** реализовать все абстрактные члены. Иначе — ошибка компиляции.

### У абстрактного метода не может быть тела

```ts
abstract class Shape {
    abstract calculateArea(): number {
        return 0;
    }
}
// ошибка TS1245: Method 'calculateArea' cannot have an implementation
// because it is marked abstract
```

`abstract` и реализация — взаимоисключающие вещи. Нужно тело — убирайте `abstract`, и метод станет обычным.

### Зачем это нужно

Добавляя треугольник, вы создаёте новый класс и реализуете в нём `calculateArea()`. В родительский класс лезть не нужно, ничего не ломается, никаких `if` не появляется. Каждый класс делает только то, что относится к нему.

На вопрос «а зачем нужен такой контроль» лектор привёл рабочий пример: в финансовой системе каждый человек обязан иметь зарплату и адрес. Абстрактный класс не даст создать класс без них.

## 6. Полиморфизм

**Полиморфизм** (polymorphism, буквально «много форм») — возможность вызвать метод с одним и тем же именем у разных классов и получить разное поведение.

Это называется **переопределением** (overriding, ключевое слово — `override`): дочерний класс объявляет метод с тем же именем, что у родителя, но со своей реализацией.

### Пример

```ts
class Human {
    constructor(public name: string) {}

    sayHi(): string {
        return `Hello, my name is ${this.name} and I like to travel.`;
    }
}

class Programmer extends Human {
    sayHi(): string {
        return `Hello, my name is ${this.name} and I write code.`;
    }
}

console.log(new Human("John").sayHi());
// Hello, my name is John and I like to travel.
console.log(new Programmer("Anna").sayHi());
// Hello, my name is Anna and I write code.
```

Имя метода одно, результат разный.

### Какой метод вызовется

Вопрос, который задали на лекции: откуда код знает, какой из двух `sayHi` брать? Ответ: **объект всегда вызывает свой собственный метод**. Объект от `Human` берёт метод из `Human`, объект от `Programmer` — из `Programmer`, и никогда наоборот.

Отсюда и практическая польза: можно работать с коллекцией разных объектов одинаково.

```ts
const people: Human[] = [new Human("John"), new Programmer("Anna")];

for (const p of people) {
    console.log(p.sayHi());   // каждый отвечает по-своему
}
```

Вызов один, поведение разное — это и есть полиморфизм.

### Вызов родительской версии: `super.метод()`

Иногда нужно не заменить родительский метод, а дополнить его.

**Базовый синтаксис:**

```ts
super.имяМетода(аргументы);
```

**Пример:**

```ts
class Teacher extends Human {
    sayHi(): string {
        return super.sayHi() + " I also teach.";
    }
}

console.log(new Teacher("Boris").sayHi());
// Hello, my name is Boris and I like to travel. I also teach.
```

Внутри `Teacher.sayHi()` вызов `super.sayHi()` обращается к версии родителя, а не к себе — иначе получилась бы бесконечная рекурсия.

### Переопределение полей

То же работает и с полями:

```ts
class Base {
    public age: number = 20;
}
class Child extends Base {
    public age: number = 25;
}

console.log(new Base().age);    // 20
console.log(new Child().age);   // 25
```

Имя одно, значения разные.

### Ограничения переопределения

Лектор сказал, что «правила есть, но мы их разбирать не будем». Правило одно и формулируется просто: **сигнатура в наследнике должна быть совместима с родительской**. Тип поля или метода менять нельзя.

Сигнатура (signature) — имя метода плюс типы его параметров и типа результата, то есть «как метод выглядит снаружи», без тела.

```ts
class Human { age: number = 20; }
class Programmer extends Human { age: string = "twenty"; }
// ошибка TS2416: Property 'age' in type 'Programmer' is not assignable
// to the same property in base type 'Human'.
//   Type 'string' is not assignable to type 'number'.
```

То же с методами — нельзя добавить обязательный параметр, которого нет у родителя:

```ts
class Human { sayHi(a: string): string { return a; } }
class Programmer extends Human {
    sayHi(a: string, b: number): string { return a + b; }
}
// ошибка TS2416: Target signature provides too few arguments.
// Expected 2 or more, but got 1.
```

Логика такая: раз объектом наследника можно пользоваться везде, где ожидался родитель, его методы обязаны принимать те же вызовы. Если дополнительный параметр нужен — сделайте его опциональным (`b?: number`).

**Уточнение (в лекции не прозвучало, но прямо относится к теме).** В TypeScript есть ключевое слово `override`, которое помечает переопределение явно:

```ts
class Programmer extends Human {
    override sayHi(): string { return "code"; }
}
```

Зачем: оно ловит опечатки. Если ошибиться в имени и написать `sayHello`, компилятор сразу скажет, что переопределять нечего:

```ts
class Teacher extends Human {
    override sayHello(): string { return "oops"; }
}
// ошибка TS4113: This member cannot have an 'override' modifier
// because it is not declared in the base class 'Human'
```

Без `override` такая опечатка создала бы просто новый метод, а старый продолжил бы работать по-родительски — баг, который ищут долго. Флаг компилятора `noImplicitOverride` делает это слово обязательным при каждом переопределении (ошибка TS4114, если забыли).

# Часть 2. Дополнительные возможности классов

## 7. `protected`

Третий модификатор доступа (access modifier), в дополнение к `public` и `private`.

### Задача

У родителя есть приватное поле. Дочерний класс хочет его изменить — и не может: `private` виден только внутри своего класса, наследникам он недоступен.

### Базовый синтаксис

```ts
class Родитель {
    protected поле: Тип = значение;
}
```

`protected` работает как `private` — снаружи класса поле не видно. Но в отличие от `private`, **любой наследник его видит**.

### Пример

```ts
class User {
    protected courseCount: number = 0;
    constructor(public login: string) {}
    getCount(): number { return this.courseCount; }
}

class Student extends User {
    updateCourseCount(): void {
        this.courseCount = 5;      // наследнику доступно
    }
}

const student = new Student("anna");
student.updateCourseCount();
console.log(student.getCount());   // 5

console.log(student.courseCount);
// ошибка TS2445: Property 'courseCount' is protected and only accessible
// within class 'User' and its subclasses
```

### Сводка по трём модификаторам

| Модификатор | Внутри своего класса | В наследнике | Снаружи |
|---|---|---|---|
| `public` | да | да | да |
| `protected` | да | да | **нет** |
| `private` | да | **нет** | нет |

**Связь с работой QA.** `protected` — именно тот модификатор, которым помечают `page` в базовом классе страницы при Page Object Model: страницы-наследники с ним работают, а тесты снаружи — нет.

## 8. Наследование интерфейсов

Наследование интерфейсов — interface inheritance.

Интерфейсы разбирали несколько лекций назад, до классов. Теперь, когда известно, что такое `extends`, к ним можно вернуться.

### Базовый синтаксис

```ts
interface Родитель {
    поле: Тип;
}

interface Ребёнок extends Родитель {
    своёПоле: Тип;
}

interface ОтДвоих extends Первый, Второй {
    своёПоле: Тип;
}
```

### Пример

```ts
interface User {
    name: string;
    email: string;
}

interface Admin extends User {
    role: string;
}

const admin: Admin = { name: "A", email: "a@b.c", role: "root" };
```

### Главное отличие от классов

**Интерфейс может наследовать от нескольких интерфейсов сразу** — через запятую. Классу так нельзя.

```ts
interface Payment {
    cardNumber: string;
}

interface Dean extends User, Payment {
    department: string;
}

const dean: Dean = {
    name: "D",
    email: "d@b.c",
    cardNumber: "1234",
    department: "QA",
};
```

Интерфейсы при этом не обязаны быть как-то связаны между собой — можно наследовать от любых.

Почему классам нельзя, а интерфейсам можно — на лекции вопрос остался открытым. Короткий ответ: интерфейс не содержит реализации, только набор требований, поэтому объединить два набора безопасно. У классов есть реализация, и при наследовании от двух родителей с одинаковым методом было бы непонятно, какую версию брать. Это известная проблема множественного наследования (multiple inheritance), её называют «ромбовидной проблемой» (diamond problem), и большинство языков её обходит именно так.

## 9. `implements` — класс реализует интерфейс

Интерфейсом можно описать не только переменную, но и требования к классу. Это называется реализацией интерфейса (implementing an interface).

### Базовый синтаксис

```ts
class ИмяКласса implements Интерфейс1, Интерфейс2 {
    // обязан содержать всё, что объявлено в интерфейсах
}
```

`implements` — зарезервированное слово. Интерфейсов можно перечислить несколько через запятую.

### Пример

```ts
interface TakePhoto {
    cameraMode: string;
    filter: string;
    burst: number;
}

interface Story {
    createStory(): void;
}

class Instagram implements TakePhoto, Story {
    constructor(
        public cameraMode: string,
        public filter: string,
        public burst: number,
    ) {}

    createStory(): void {
        console.log("story created");
    }
}
```

Если что-то из интерфейса не реализовать, компилятор это поймает:

```ts
class Instagram implements TakePhoto {
    constructor(public cameraMode: string) {}
}
// ошибка TS2420: Class 'Instagram' incorrectly implements interface 'TakePhoto'.
//   Property 'burst' is missing in type 'Instagram' but required in type 'TakePhoto'
```

### Зачем это нужно

Если в будущем появятся классы `Facebook`, `TikTok` и другие с теми же требованиями, набор свойств описывается один раз в интерфейсе, а классы просто его реализуют. Все правила интерфейсов продолжают действовать: опциональные свойства остаются опциональными, `readonly` остаётся `readonly`.

**Уточнение (важное, в лекции не прозвучало).** `implements` — проверка **только на этапе компиляции**. В скомпилированном JavaScript от интерфейса и от слова `implements` не остаётся ничего:

```js
// результат компиляции класса Instagram
class Instagram {
    cameraMode;
    constructor(cameraMode) {
        this.cameraMode = cameraMode;
    }
}
```

Ни интерфейсов, ни `implements` в выводе нет — они существуют только для компилятора.

Практическое следствие для QA: проверить в рантайме, что объект «реализует интерфейс», невозможно — `instanceof` с интерфейсом не работает, его просто нет. А вот с абстрактным классом работает, потому что абстрактный класс после компиляции остаётся обычным классом:

```ts
console.log(circle instanceof Shape);   // true
```

## 10. Интерфейс или абстрактный класс

Вопрос несколько раз возникал на лекции («интерфейс тут выступает как абстрактный класс?»), и ответ сводился к «это две разные вещи». Разница существенная, и её спрашивают на собеседованиях.

| | Интерфейс | Абстрактный класс |
|---|---|---|
| Реализация методов | нельзя, только подписи | можно: абстрактные + обычные методы |
| Поля со значениями | нет | есть |
| Конструктор | нет | есть |
| Модификаторы доступа | нет | `public` / `protected` / `private` |
| Сколько можно применить к классу | **несколько** (`implements A, B`) | **один** (`extends A`) |
| Существует после компиляции | нет | да |
| `instanceof` | не работает | работает |

Практическое правило: **интерфейс — это контракт, абстрактный класс — это контракт плюс общий код.** Если наследникам нечего разделять, кроме набора требований, берите интерфейс. Если есть общая реализация, которую не хочется дублировать (как метод `describe()` в примере с фигурами), нужен абстрактный класс.

**Связь с работой QA.** В Page Object Model обычно встречается именно абстрактный класс: базовый класс страницы хранит `protected page` и общие методы (`open()`, `waitForLoad()`), а конкретные страницы его наследуют. Интерфейсом описывают контракт, когда общего кода нет.

## 12. Шпаргалка и типичные ошибки

### Синтаксис на одной странице

```ts
// наследование
class Parent {
    constructor(public name: string) {}
    greet(): string { return `Hi, ${this.name}`; }
}

class Child extends Parent {
    constructor(name: string, public extra: string) {
        super(name);               // всегда первой строкой
    }
    override greet(): string {     // полиморфизм
        return super.greet() + "!";
    }
}

// абстрактный класс
abstract class Shape {
    constructor(public color: string) {}
    abstract calculateArea(): number;      // правило, без тела
    describe(): void {                     // обычный метод, с телом
        console.log(this.calculateArea());
    }
}

class Circle extends Shape {
    constructor(color: string, private radius: number) { super(color); }
    calculateArea(): number { return Math.PI * this.radius ** 2; }
}

// модификаторы
class User {
    public login: string = "";
    protected courseCount: number = 0;     // виден наследникам
    private password: string = "";         // только своему классу
}

// интерфейсы
interface A { x: number; }
interface B { y: number; }
interface C extends A, B { z: number; }    // несколько — можно

class Impl implements A, B {               // несколько — можно
    constructor(public x: number, public y: number) {}
}
```

### Четыре принципа одной строкой

| Принцип | Ключевые слова | Суть |
|---|---|---|
| Наследование (inheritance) | `extends`, `super` | ребёнок получает всё от родителя |
| Инкапсуляция (encapsulation) | `private`, `protected`, `public` | класс решает, что показать |
| Абстракция (abstraction) | `abstract` | что делает объект, а не как |
| Полиморфизм (polymorphism) | переопределение (overriding), `override`, `super.метод()` | одно имя — разное поведение |

### Термины по-английски

| Русский | Английский |
|---|---|
| ООП | object-oriented programming (OOP) |
| класс-родитель, базовый класс, суперкласс | parent class, base class, superclass |
| дочерний (производный) класс | child class, derived class, subclass |
| создать экземпляр («инстанцировать») | instantiate |
| переопределение | overriding |
| модификаторы доступа | access modifiers |
| реализация интерфейса | implementing an interface |
| множественное наследование / «ромбовидная проблема» | multiple inheritance / diamond problem |

### Коды ошибок, которые встретятся

| Ошибка | Когда |
|---|---|
| TS2511 | `new` от абстрактного класса |
| TS2515 | наследник не реализовал абстрактный член |
| TS1245 | у абстрактного метода есть тело |
| TS1174 | `extends` от двух классов |
| TS2445 | обращение к `protected` снаружи |
| TS2341 | обращение к `private` снаружи |
| TS2416 | несовместимая сигнатура при переопределении |
| TS2420 | класс не реализовал всё из интерфейса |
| TS17009 | `this` раньше `super(...)` |
| TS4113 / TS4114 | проблемы с `override` |

### Частые ошибки

1. **Поставить `this` раньше `super(...)`** в конструкторе наследника.
2. **Забыть `super(...)`**, когда у родителя есть параметры конструктора.
3. **Перепутать порядок аргументов в `super(...)`** — он важен, компилятор поймает только несовпадение типов.
4. **Попытаться унаследовать класс от двух родителей** — так можно только с интерфейсами.
5. **Создать объект от абстрактного класса** — он шаблон, а не класс.
6. **Написать тело у абстрактного метода** — тогда он не абстрактный.
7. **Забыть реализовать абстрактный член** в наследнике.
8. **Поменять тип поля или метода при переопределении** — сигнатура должна оставаться совместимой.
9. **Опечататься в имени переопределяемого метода** — без `override` вместо переопределения получится новый метод, а старый продолжит работать по-родительски.
10. **Использовать `private` там, где нужен `protected`** — наследники перестанут видеть поле.
11. **Рассчитывать, что `private` скрывает данные в рантайме** — он их не скрывает.
12. **Ждать, что `implements` что-то проверит во время выполнения** — интерфейсы после компиляции исчезают полностью.
