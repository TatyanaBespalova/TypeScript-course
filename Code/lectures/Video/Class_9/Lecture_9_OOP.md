## Часть 1. Введение в ООП и наследование

### 1. Что такое OOP

#### Материал лекции

OOP — объектно-ориентированное программирование. Лектор определяет его как подход, при котором программа рассматривается как набор классов и созданных от них объектов.

Каждый объект:

- имеет собственные характеристики;
- имеет собственное поведение;
- может взаимодействовать с другими объектами;
- получает параметры и возвращает результат.

По словам лектора, этот подход отличается от написания программы строго сверху вниз, когда каждая следующая строка зависит от предыдущей. OOP используется в TypeScript, Java, C# и других языках.

Лектор называет четыре основных принципа OOP:

1. Наследование — inheritance.
2. Инкапсуляция — encapsulation.
3. Абстракция — abstraction.
4. Полиморфизм — polymorphism.

Использование одного или нескольких этих принципов означает применение OOP.

#### Преимущество OOP по объяснению лектора

Можно работать с уже готовыми объектами и использовать их результат, не всегда зная внутреннее устройство объекта. Вместо работы только с последовательностью строк программа строится из взаимодействующих частей.

#### Простой пример идеи объекта

В лекции объект автомобиля описывается через характеристики и поведение:

```ts
class Car {
  public name: string;

  constructor(name: string) {
    this.name = name;
  }

  getName(): string {
    return `This is a ${this.name}.`;
  }
}

const car = new Car("Toyota");
console.log(car.getName());
```

Здесь:

- `Car` — класс;
- `car` — объект, созданный от класса;
- `name` — характеристика объекта;
- `getName()` — поведение объекта.

> **В лекции изложено невнятно:** отличие OOP от последовательного выполнения кода описано общими словами. Не объясняется, что код внутри методов всё равно выполняется последовательно.

#### Дополнения от AI

OOP не отменяет последовательное выполнение команд. Оно помогает организовать программу: связанные данные и действия объединяются в классы и объекты. Внешний код обращается к объекту через его доступные свойства и методы.

### 2. Наследование: родительский и дочерний классы

#### Материал лекции

Наследование позволяет создавать один класс на основе другого.

- Исходный класс называется родительским классом или superclass.
- Новый класс называется дочерним классом или классом-ребёнком.
- Дочерний класс получает поля и методы родителя.
- Одновременно дочерний класс может иметь собственные поля и методы.

Лектор начинает с автомобиля, у которого могут быть имя, цвет, модель, год выпуска и другие характеристики. Если добавить всё в один большой класс, в нём появится много свойств, часть которых придётся делать необязательными. По объяснению лектора, это увеличивает объём ручной работы и вероятность ошибок.

#### Простой пример: базовый класс `Car`

```ts
class Car {
  public name: string;

  constructor(name: string) {
    this.name = name;
  }

  getName(): string {
    return `This is a ${this.name}.`;
  }
}
```

Класс хранит имя автомобиля и предоставляет метод `getName()`.

#### Пример среднего уровня: `Color extends Car`

```ts
class Color extends Car {
  public color: string;

  constructor(name: string, color: string) {
    super(name);
    this.color = color;
  }

  getColor(): string {
    return `The color is ${this.color}.`;
  }
}

const color = new Color("Toyta", "Red");

console.log(color.getColor());
console.log(color.getName());
```

`Color` содержит собственные элементы:

- поле `color`;
- метод `getColor()`.

Одновременно объект `color` получает от `Car`:

- поле `name`;
- метод `getName()`.

#### Ключевое слово `extends`

Запись

```ts
class Color extends Car
```

означает, что `Color` наследуется от `Car`. В показанном примере `Car` — родитель, а `Color` — ребёнок.

> **В лекции изложено невнятно:** во время обсуждения прозвучало, что разработчик просто выбирает, какой из двух классов будет родителем, и что принципиальной разницы нет. Критерий выбора родителя и ребёнка не был раскрыт.

#### Дополнения от AI

Направление наследования обычно определяется смысловой связью: дочерний класс должен быть более конкретным вариантом родительского. Например, `ElectricCar` является разновидностью `Car`. Одного желания связать два класса недостаточно — между ними должна быть понятная логическая связь.

### 3. Конструктор дочернего класса и `super()`

#### Материал лекции

Дочерний класс получает `name` для родительского класса и `color` для себя:

```ts
constructor(name: string, color: string) {
  super(name);
  this.color = color;
}
```

Лектор объясняет `super(name)` как команду: перейти в конструктор родителя и выполнить то, что требуется родительскому конструктору. Поскольку конструктору `Car` нужно имя, дочерний класс передаёт ему `name`.

Порядок действий в примере:

1. `new Color("Toyta", "Red")` передаёт два аргумента.
2. Параметр `name` передаётся родителю через `super(name)`.
3. Родительский конструктор выполняет `this.name = name`.
4. После этого дочерний конструктор выполняет `this.color = color`.

#### Передача нескольких значений

В более длинной цепочке лектор передаёт родителю несколько параметров через запятую:

```ts
constructor(name: string, model: string, type: string) {
  super(name, model);
  this.type = type;
}
```

Лектор подчёркивает, что имена параметров можно изменить, но важен порядок: значения в `super(...)` должны соответствовать параметрам родительского конструктора.

> **В лекции изложено невнятно:** в ответах на вопросы правила использования `super()` описываются противоречиво. В частности, обсуждаются пустой конструктор, отсутствие конструктора и доступ к унаследованным свойствам, но единое правило не формулируется. Также звучит предположение, что без явного конструктора доступ к родительскому `name` может отсутствовать.

#### Дополнения от AI

- Если в дочернем классе объявлен собственный конструктор, до обращения к `this` необходимо вызвать `super(...)`.
- Если дочерний класс не объявляет конструктор, используется автоматически созданный конструктор, передающий аргументы родителю.
- Унаследованные доступные поля и методы не исчезают только потому, что в дочернем классе не написан собственный конструктор.
- `super.methodName()` можно использовать для вызова доступного метода родительского класса.

Пример с пустым дочерним классом:

```ts
class NamedCar extends Car {}

const namedCar = new NamedCar("Toyota");
console.log(namedCar.getName());
```

Этот дополнительный пример не демонстрировался лектором; он приведён только для уточнения правила.

### 4. Несколько дочерних классов одного родителя

#### Материал лекции

От одного родительского класса могут наследоваться несколько классов. В лекции `Color` и `Model` находятся на одном уровне и отдельно наследуются от `Car`.

```ts
class Model extends Car {
  public model: string;

  constructor(name: string, model: string) {
    super(name);
    this.model = model;
  }

  getModel(): string {
    return `Model is ${this.model}.`;
  }
}

const model = new Model("Toyota", "Camry");

console.log(model.getModel());
console.log(model.getName());
console.log(model.name);
```

Объект `model` имеет:

- собственное поле `model`;
- собственный метод `getModel()`;
- унаследованное поле `name`;
- унаследованный метод `getName()`.

#### Отношения между `Color` и `Model`

По объяснению лектора:

- `Color` видит доступные элементы `Car`;
- `Model` видит доступные элементы `Car`;
- `Color` и `Model` не наследуются друг от друга;
- поэтому они не получают собственные поля и методы друг друга.

Схема:

```text
        Car
       /   \
   Color   Model
```

> **В лекции изложено невнятно:** слушатели спрашивают, как получить один объект машины одновременно с цветом и моделью. Лектор откладывает этот вопрос и ограничивает текущую задачу демонстрацией двух независимых наследников. Полное решение в рассматриваемых четырёх частях не приводится.

#### Дополнения от AI

В рамках именно этого фрагмента важно запомнить только показанное отношение: два дочерних класса могут иметь общего родителя и при этом не быть связанными друг с другом. Способ объединения цвета и модели в одном объекте здесь не следует считать объяснённым.

### 5. Многоуровневое наследование

#### Материал лекции

Лектор строит цепочку из трёх классов:

```text
Car → Model → Type
```

- `Model` наследуется от `Car`.
- `Type` наследуется от `Model`.
- Поэтому `Type` получает доступные элементы и `Model`, и `Car`.

#### Пример среднего уровня: `Type extends Model`

```ts
class Type extends Model {
  public type: string;

  constructor(name: string, model: string, type: string) {
    super(name, model);
    this.type = type;
  }

  getType(): string {
    return `This car is a ${this.type}.`;
  }
}

const type = new Type("Toyota", "Camry", "sedan");

console.log(type.getType());
console.log(type.getModel());
console.log(type.getName());
```

Объект `type` получает:

| Источник | Полученные элементы |
|---|---|
| `Car` | `name`, `getName()` |
| `Model` | `model`, `getModel()` |
| `Type` | `type`, `getType()` |

`Color` не входит в эту цепочку, поэтому его поле и метод объекту `type` не передаются.

#### Направление доступности

Лектор описывает наследование как движение снизу вверх по цепочке:

- `Car` знает только собственные элементы;
- `Model` получает элементы `Car`, но не знает о содержимом `Type`;
- `Type` получает элементы `Model` и `Car`.

#### Дополнения от AI

Родительский класс не получает элементы своих наследников. Наследование распространяет доступные поля и методы от более общего класса к более конкретному, а не в обратную сторону.

### 6. Основные правила наследования из лекции

Лектор подводит следующий итог:

1. Один дочерний класс может напрямую наследоваться только от одного родительского класса.
2. Один класс не может одновременно написать `extends` для двух разных классов.
3. От одного родителя может наследоваться несколько дочерних классов.
4. Цепочку наследования можно продолжать: один наследник может стать родителем следующего класса.
5. Дочерний класс получает родительские поля и методы.
6. Значения для родительского конструктора передаются через `super(...)`.
7. В дочернем конструкторе сначала выполняется `super(...)`, затем инициализируются собственные поля.

#### Простой пример: несколько наследников

```ts
class Color extends Car {
  // собственные поле color и метод getColor()
}

class Model extends Car {
  // собственные поле model и метод getModel()
}
```

#### Пример среднего уровня: цепочка

```ts
class Car {}
class Model extends Car {}
class Type extends Model {}
```

`Type` находится в конце цепочки и наследует доступные элементы предыдущих классов.

### 7. Порядок объявления классов, import/export и hoisting

#### Материал лекции

Во время вопросов обсуждается, обязательно ли записывать родительский класс в файле раньше дочернего.

Лектор говорит:

- важнее, чтобы нужный класс существовал;
- родитель и ребёнок часто находятся в разных файлах;
- в таком случае используются `export` и `import`;
- для чистоты кода желательно сначала показывать базовый класс, затем дочерний;
- эту ситуацию не следует называть hoisting.

> **В лекции изложено невнятно:** сначала говорится, что родитель нужно написать раньше, а затем — что порядок не имеет значения. Условия, при которых порядок действительно допустим, не разграничены.

#### Дополнения от AI

Если классы находятся в разных модулях, дочерний класс импортирует родителя и может быть расположен в отдельном файле. В одном выполняемом файле безопасный и понятный порядок — сначала объявить родителя, затем класс с `extends`.

Пример структуры:

```ts
// Car.ts
export class Car {}
```

```ts
// Model.ts
import { Car } from "./Car";

export class Model extends Car {}
```

Этот пример добавлен AI для пояснения упомянутых лектором `import` и `export`.

### 8. Начало темы инкапсуляции

#### Материал лекции

Инкапсуляция — следующий принцип OOP. По определению лектора, объект или класс решает:

- какую информацию раскрывать внешнему миру;
- какую информацию не раскрывать.

Лектор связывает инкапсуляцию с публичными и приватными полями и методами, рассмотренными на предыдущем занятии.

#### Пример из лекции: `Employee`

```ts
class Employee {
  public name: string;
  public age: number;
  public baseSalary: number;
  public monthlyBonus: number = 1000;

  constructor(name: string, age: number, baseSalary: number) {
    this.name = name;
    this.age = age;
    this.baseSalary = baseSalary;
  }

  calculateSalary(): void {
    const overallSalary = this.baseSalary + this.monthlyBonus;
    console.log(`My overall salary is $${overallSalary}.`);
  }

  getDetails(): void {
    console.log(`Name: ${this.name}, age: ${this.age}`);
  }
}

const e1 = new Employee("John", 30, 2000);
e1.getDetails();
e1.calculateSalary();
```

#### Две проблемы, обозначенные лектором

1. Метод `calculateSalary()` доступен снаружи, поэтому внешний код видит способ расчёта общей зарплаты.
2. Поле `monthlyBonus` публичное, поэтому его можно изменить снаружи:

```ts
e1.monthlyBonus = 5000;
e1.calculateSalary();
```

После изменения бонуса внешний код влияет на итоговую зарплату объекта. Лектор считает, что расчёт зарплаты и возможность произвольно изменять его внутренние составляющие не должны быть открыты пользователю класса.

> **Материал в этой части изложен не полностью:** фрагмент заканчивается после постановки проблемы. Применение `private` и окончательный вариант класса будут показаны в следующих частях лекции, поэтому здесь решение не добавляется.

#### Дополнения от AI

На этом этапе достаточно зафиксировать цель инкапсуляции: ограничить внешний доступ к деталям, которыми объект должен управлять самостоятельно. Конкретное решение лучше дописать после обработки следующего фрагмента лекции, чтобы не опережать лектора.

---

### Краткая памятка

```ts
class Parent {
  constructor(public parentValue: string) {}

  getParentValue(): string {
    return this.parentValue;
  }
}

class Child extends Parent {
  constructor(parentValue: string, public childValue: string) {
    super(parentValue);
  }
}
```

- `extends` — наследование от другого класса.
- `super(...)` — вызов конструктора родителя.
- Наследник получает доступные поля и методы родителя.
- Наследник может добавлять собственные поля и методы.
- Несколько детей могут иметь одного родителя.
- Один класс напрямую наследуется только от одного класса.
- Родитель не получает элементы дочернего класса.

## Часть 2. Инкапсуляция и абстрактные классы

### 1. Продолжение инкапсуляции: защита расчёта зарплаты

В предыдущей части был создан класс `Employee`. Проблема заключалась в том, что внешний код мог менять бонус и непосредственно вызывать расчёт зарплаты. Лектор закрывает эти детали словом `private`.

```ts
class Employee {
  public name: string;
  public age: number;
  public baseSalary: number;
  private monthlyBonus: number = 1000;

  constructor(name: string, age: number, baseSalary: number) {
    this.name = name;
    this.age = age;
    this.baseSalary = baseSalary;
  }

  private calculateSalary(): void {
    const overallSalary = this.baseSalary + this.monthlyBonus;
    console.log(`My overall salary is $${overallSalary}.`);
  }

  getDetails(): void {
    console.log(`Name: ${this.name}, age: ${this.age}`);
    this.calculateSalary();
  }
}

const e1 = new Employee("John", 30, 2000);
e1.getDetails();
```

Что изменилось:

- `monthlyBonus` закрыт: внешний код не может произвольно изменить бонус;
- `calculateSalary()` закрыт: способ вычисления полной зарплаты остаётся внутренней деталью класса;
- `getDetails()` остаётся доступным снаружи и вызывает закрытый метод внутри класса.

#### Простой пример

```ts
const employee = new Employee("Ann", 25, 2500);
employee.getDetails(); // допустимо

// employee.monthlyBonus = 5000; // ошибка: private
// employee.calculateSalary();   // ошибка: private
```

#### Пример среднего уровня

Лектор отдельно показывает, что открытое поле всё ещё можно изменить:

```ts
const employee = new Employee("John", 30, 2000);

employee.baseSalary = 6000;
employee.getDetails();
// Общая зарплата будет рассчитана уже на основе новой baseSalary.
```

То есть инкапсуляция действует только на те члены класса, которые действительно помечены как `private`.

#### Что важно запомнить

По формулировке лектора, инкапсуляция полезна, когда свойства или методы нужны исключительно для внутренних процессов и не должны быть доступны снаружи. Закрытый доступ также не позволяет случайно или намеренно изменить эти данные через объект.

#### В лекции изложено невнятно

Лектор говорит, что пользователь класса «не видит», как вычисляется зарплата. При этом ученики справедливо замечают, что автор класса видит код метода. Различие между чтением исходного файла и доступом через экземпляр класса проговаривается не сразу.

> **Дополнения от AI**  
> Здесь полезно различать две роли. Автор класса видит реализацию, потому что пишет или читает исходный код. Пользователь экземпляра работает через доступные члены объекта: `private` не позволяет ему обратиться к `monthlyBonus` и `calculateSalary()` через `employee`. В рамках примера «скрытие» означает ограничение доступа средствами TypeScript, а не обязательное сокрытие текста исходного кода.

### 2. Одновременное применение принципов ООП

На вопрос, можно ли разбить пример на несколько классов, лектор отвечает: да. После изучения наследования и инкапсуляции их можно применять вместе.

- `extends` позволяет построить связь родительского и дочернего классов;
- `private` скрывает внутренние детали;
- несколько принципов ООП могут использоваться в одном примере.

#### Простой пример

```ts
class Person {
  constructor(public name: string) {}
}

class Employee extends Person {
  private bonus = 1000;
}
```

Здесь `Employee` наследуется от `Person`, а `bonus` инкапсулирован.

#### Пример среднего уровня

```ts
class Person {
  constructor(public name: string) {}

  introduce(): void {
    console.log(`My name is ${this.name}`);
  }
}

class Employee extends Person {
  constructor(name: string, public baseSalary: number, private bonus: number) {
    super(name);
  }

  showSalary(): void {
    console.log(this.baseSalary + this.bonus);
  }
}

const employee = new Employee("John", 2000, 1000);
employee.introduce();
employee.showSalary();
```

### 3. Абстракция: общая идея

Следующий принцип — абстракция. По объяснению лектора, класс или процесс должен предоставлять только ту информацию, которая нужна для конкретной задачи. Объект открывает нужные поля и методы, а лишние детали не раскрываются.

Лектор рассматривает приложение для рисования фигур: кругов, квадратов, треугольников и других.

#### Почему один обычный класс становится неудобным

Если хранить вид фигуры в одном поле, методы придётся строить на цепочках условий:

```ts
class Shape {
  constructor(public type: string) {}

  calculateArea(): number {
    if (this.type === "circle") {
      // расчёт круга
    } else if (this.type === "square") {
      // расчёт квадрата
    }

    return 0;
  }
}
```

При добавлении новой фигуры пришлось бы возвращаться в этот метод и дописывать ещё одну проверку. Лектор называет такой подход возможным, но долгим и проблематичным.

#### Решение из лекции

Создать класс-шаблон, который:

- содержит общие возможности фигур;
- задаёт обязательные правила;
- оставляет реализацию уникальных действий конкретным классам-наследникам.

Такой шаблон называется **абстрактным классом**.

#### Простой пример идеи

```ts
abstract class Shape {}
```

Ключевое слово `abstract` показывает, что `Shape` — не самостоятельная конкретная фигура, а шаблон.

#### Пример среднего уровня

```ts
abstract class Shape {
  constructor(public color: string) {}

  abstract calculateArea(): number;
}
```

Здесь шаблон требует, чтобы у будущей фигуры был цвет и метод вычисления площади.

### 4. Свойство класса через параметр конструктора

Во время создания `Shape` лектор повторяет две формы записи свойства.

#### Полная запись

```ts
class A1 {
  public color: string;

  constructor(color: string) {
    this.color = color;
  }
}
```

Здесь:

- `public color: string` — поле экземпляра;
- `color` в параметрах конструктора — локальный параметр;
- `this.color = color` сохраняет полученный аргумент в поле экземпляра.

#### Сокращённая запись TypeScript

```ts
class A2 {
  constructor(public color: string) {}
}
```

По лекции это сокращение той же конструкции: TypeScript создаёт поле и присваивает ему значение параметра.

#### Пример среднего уровня: несколько свойств

```ts
class Box {
  constructor(
    public color: string,
    public size: string
  ) {}
}

const box = new Box("red", "large");
console.log(box.color);
console.log(box.size);
```

Без сокращения каждое поле пришлось бы отдельно объявить, принять в конструкторе и присвоить через `this`.

#### В лекции изложено невнятно

Объяснение различия между полем `this.color` и параметром `color` вызвало несколько повторных вопросов. Фраза о том, что это «абсолютно разные переменные», не сразу связывается с сокращённой записью, где визуально остаётся только один `color`.

> **Дополнения от AI**  
> В полной записи параметр `color` существует только во время выполнения конструктора, а `this.color` принадлежит созданному объекту. Запись `constructor(public color: string) {}` просит TypeScript выполнить оба шага автоматически: создать публичное поле `color` и записать в него аргумент конструктора.

### 5. Абстрактный класс `Shape`

Лектор формулирует два правила для будущих фигур:

1. каждая фигура должна иметь цвет;
2. каждая фигура должна уметь вычислять площадь.

```ts
abstract class Shape {
  constructor(public color: string) {}

  abstract calculateArea(): number;

  describe(): void {
    console.log(
      `This is a ${this.color} shape with an area of ${this.calculateArea()}.`
    );
  }
}
```

#### Абстрактный метод

```ts
abstract calculateArea(): number;
```

По лекции:

- это обязательное правило для дочерних классов;
- у абстрактного метода нет тела;
- он сообщает имя метода и тип возвращаемого значения;
- конкретную формулу напишет класс-наследник.

Нельзя написать тело абстрактного метода:

```ts
abstract calculateArea(): number {
  return 0;
}
```

#### Обычный метод в абстрактном классе

Абстрактный класс может содержать обычные методы с готовой реализацией:

```ts
describe(): void {
  console.log(
    `This is a ${this.color} shape with an area of ${this.calculateArea()}.`
  );
}
```

Метод `describe()` общий для всех фигур. Он использует `color` и вызывает `calculateArea()`, реализацию которого предоставит конкретная фигура.

#### Экземпляр абстрактного класса создать нельзя

```ts
// const shape = new Shape("red"); // ошибка
```

Лектор подчёркивает: абстрактный класс служит шаблоном для будущих классов и сам не создаётся через `new`.

#### Простой пример

```ts
abstract class Message {
  abstract getText(): string;
}
```

#### Пример среднего уровня

```ts
abstract class Message {
  constructor(public author: string) {}

  abstract getText(): string;

  print(): void {
    console.log(`${this.author}: ${this.getText()}`);
  }
}
```

Этот пример иллюстрирует ту же структуру, что и `Shape`: обязательный параметр, абстрактный метод и общий обычный метод.

### 6. Конкретный класс `Circle`

Чтобы использовать шаблон `Shape`, лектор создаёт дочерний класс `Circle`.

```ts
class Circle extends Shape {
  constructor(public color: string, private radius: number) {
    super(color);
  }

  calculateArea(): number {
    return Math.PI * this.radius ** 2;
  }
}
```

Разбор:

- `extends Shape` — круг наследуется от абстрактного класса;
- `color` передаётся родительскому конструктору через `super(color)`;
- `radius` нужен для расчёта площади;
- `radius` сделан `private`, чтобы его нельзя было менять снаружи;
- `calculateArea()` реализует обязательное правило абстрактного класса.

Если не реализовать `calculateArea()`, TypeScript сообщает, что класс не реализует абстрактный член.

#### Простой пример использования

```ts
const circle = new Circle("red", 5);

circle.describe();
console.log(circle.calculateArea());
```

Результат из лекции:

```text
This is a red shape with an area of 78.53981633974483.
78.53981633974483
```

#### Пример среднего уровня

```ts
const smallCircle = new Circle("blue", 2);
const largeCircle = new Circle("green", 10);

smallCircle.describe();
largeCircle.describe();

// smallCircle.radius = 5; // ошибка: radius — private
```

Оба объекта наследуют общий `describe()`, но площадь вычисляется реализацией `Circle`.

### 7. Три принципа ООП в одном примере

Лектор подчёркивает, что в примере с фигурами одновременно применяются три принципа:

| Принцип | Где проявляется |
|---|---|
| Наследование | `class Circle extends Shape` |
| Инкапсуляция | `private radius: number` |
| Абстракция | `abstract class Shape` и `abstract calculateArea()` |

`Circle` также получает обычный метод `describe()` от `Shape`. Абстрактный класс может содержать обычные поля, методы, конструктор, а по ответу лектора — также геттеры и сеттеры. Но экземпляр самого абстрактного класса создать нельзя.

#### Простой пример совместного применения

```ts
abstract class Figure {
  abstract area(): number;
}

class Square extends Figure {
  constructor(private side: number) {
    super();
  }

  area(): number {
    return this.side ** 2;
  }
}
```

#### Пример среднего уровня

```ts
abstract class Figure {
  constructor(public color: string) {}

  abstract area(): number;

  print(): void {
    console.log(`${this.color}: ${this.area()}`);
  }
}

class Square extends Figure {
  constructor(color: string, private side: number) {
    super(color);
  }

  area(): number {
    return this.side ** 2;
  }
}

const square = new Square("yellow", 4);
square.print();
```

## Часть 3. Абстракция и полиморфизм

### 1. Разные реализации правила абстрактного класса

В предыдущей части абстрактный класс `Shape` установил два правила:

1. фигура должна иметь цвет;
2. фигура должна реализовать метод `calculateArea()`.

```ts
abstract class Shape {
  constructor(public color: string) {}

  abstract calculateArea(): number;

  describe(): void {
    console.log(
      `This is a ${this.color} shape with an area of ${this.calculateArea()}.`
    );
  }
}
```

`calculateArea()` — абстрактный метод без тела. Конкретные классы обязаны реализовать его самостоятельно. Обычный метод `describe()` уже имеет реализацию и наследуется без дублирования.

#### Простой пример: `Circle`

```ts
class Circle extends Shape {
  constructor(public color: string, private radius: number) {
    super(color);
  }

  calculateArea(): number {
    return Math.PI * this.radius ** 2;
  }
}

const circle = new Circle("red", 5);
circle.describe();
```

#### Пример среднего уровня: `Rectangle`

```ts
class Rectangle extends Shape {
  constructor(
    public color: string,
    private width: number,
    private height: number
  ) {
    super(color);
  }

  calculateArea(): number {
    return this.width * this.height;
  }
}

const rectangle = new Rectangle("blue", 2, 2);
rectangle.describe();
```

Результат для прямоугольника:

```text
This is a blue shape with an area of 4.
```

Главное различие:

- `Circle` использует радиус и формулу `Math.PI * radius ** 2`;
- `Rectangle` использует ширину и высоту: `width * height`;
- оба класса соблюдают одинаковое правило `Shape`.

---

### 2. Зачем нужен обязательный абстрактный метод

Лектор объясняет: если убрать из `Shape` строку

```ts
abstract calculateArea(): number;
```

то исчезнет обязательное правило. Каждый дочерний класс сможет сам решать, создавать ли ему метод вычисления площади.

#### Простой пример без обязательного правила

```ts
abstract class Shape {
  constructor(public color: string) {}
}

class Circle extends Shape {
  // calculateArea() больше не обязателен
}
```

#### Пример среднего уровня с обязательным правилом

```ts
abstract class Shape {
  constructor(public color: string) {}
  abstract calculateArea(): number;
}

class Triangle extends Shape {
  constructor(
    color: string,
    private base: number,
    private height: number
  ) {
    super(color);
  }

  calculateArea(): number {
    return (this.base * this.height) / 2;
  }
}
```

Теперь `Triangle` обязан реализовать `calculateArea()`. При добавлении новой фигуры не нужно изменять `Shape`, `Circle` или `Rectangle`: создаётся новый дочерний класс со своей логикой.

По объяснению лектора, это особенно важно в больших системах, где для объектов обязательны определённые данные или действия. Правила задают разработчики, проектирующие систему.

#### В лекции изложено невнятно

Практическая причина контроля сначала объясняется словами «потому что мы так хотим». Позднее приводится пример большой системы, в которой каждый объект должен обязательно иметь определённые данные, например email или адрес. Связь этого примера с абстрактными методами проговаривается кратко.

> **Дополнения от AI**  
> Абстрактный член нужен, когда отсутствие определённого свойства или метода сделает конкретный класс неполноценным для общей задачи. В примере все фигуры должны участвовать в расчёте площади, поэтому компилятор проверяет наличие `calculateArea()` у каждого конкретного наследника.

### 3. Цвет фигуры и `super(color)`

Абстрактный класс принимает цвет:

```ts
constructor(public color: string) {}
```

Дочерний класс получает цвет через свой конструктор и передаёт его родителю:

```ts
class Rectangle extends Shape {
  constructor(
    public color: string,
    private width: number,
    private height: number
  ) {
    super(color);
  }

  calculateArea(): number {
    return this.width * this.height;
  }
}
```

Лектор подчёркивает: родительскому классу неважно, откуда пришло значение. Важно, чтобы дочерний класс передал цвет.

#### Простой пример: фиксированное значение

```ts
class RedRectangle extends Shape {
  constructor(private width: number, private height: number) {
    super("red");
  }

  calculateArea(): number {
    return this.width * this.height;
  }
}
```

В этом варианте все экземпляры будут красными.

#### Пример среднего уровня: разные значения у экземпляров

```ts
const blueRectangle = new Rectangle("blue", 2, 2);
const greenRectangle = new Rectangle("green", 4, 5);

blueRectangle.describe();
greenRectangle.describe();
```

Чтобы разные экземпляры имели разные цвета, значение передаётся снаружи при создании объекта.

#### В лекции изложено невнятно

Во время обсуждения модификатора `public` прозвучали противоречивые формулировки. Сначала ученики уточняют, можно ли оставить в конструкторе просто параметр `color: string`, затем лектор говорит, что без `public` параметр «всё равно public», но одновременно называет такую запись неправильной и отправляет к предыдущей лекции. Различие между параметром конструктора и полем класса остаётся неразрешённым.

> **Дополнения от AI**  
> В TypeScript `constructor(color: string)` создаёт только параметр конструктора. Он не становится полем объекта автоматически. Запись `constructor(public color: string)` — специальное сокращение, которое одновременно объявляет публичное поле и принимает значение. Однако дочернему классу не обязательно повторно создавать поле `color`, если оно уже создано родителем: он может принять обычный параметр `color: string` и передать его в `super(color)`.

```ts
class Rectangle extends Shape {
  constructor(
    color: string,
    private width: number,
    private height: number
  ) {
    super(color);
  }

  calculateArea(): number {
    return this.width * this.height;
  }
}
```

### 4. Итог по абстракции

Формулировка лектора:

- абстракция скрывает сложные детали реализации;
- пользователю предоставляется только нужная информация;
- внимание направлено на то, **что** делает объект, а не на то, **как** он это делает;
- абстрактный класс определяет структуру;
- дочерние классы создают конкретную реализацию;
- экземпляр абстрактного класса напрямую создать нельзя.

#### Простой пример

```ts
abstract class Animal {
  abstract makeSound(): string;
}
```

`Animal` задаёт, что животное должно уметь издавать звук, но не определяет конкретный звук.

#### Пример среднего уровня

```ts
abstract class Animal {
  constructor(public name: string) {}

  abstract makeSound(): string;

  introduce(): void {
    console.log(`${this.name}: ${this.makeSound()}`);
  }
}

class Dog extends Animal {
  makeSound(): string {
    return "Woof";
  }
}

const dog = new Dog("Rex");
dog.introduce();
```

#### Абстракция и инкапсуляция

По лекции, эти принципы часто работают вместе и их не следует путать:

| Принцип | Роль в объяснении лектора |
|---|---|
| Инкапсуляция | Помогает скрыть детали работы внутри класса |
| Абстракция | Определяет структуру и способ взаимодействия с классом |

Лектор также подтверждает, что один абстрактный класс может расширять другой абстрактный класс, если это требуется архитектурой.

### 5. Полиморфизм

Полиморфизм — четвёртый принцип ООП. Лектор переводит термин как «множество форм» и объясняет его как возможность использовать метод с одинаковым именем в связанных наследованием классах, но получать разное поведение.

#### Родительский класс `Human`

```ts
class Human {
  constructor(public name: string) {}

  sayHi(): string {
    return `Hello, my name is ${this.name} and I like travelling.`;
  }
}

const h = new Human("John");
console.log(h.sayHi());
```

Результат:

```text
Hello, my name is John and I like travelling.
```

#### Дочерний класс `Programmer`

```ts
class Programmer extends Human {
  constructor(public name: string) {
    super(name);
  }

  sayHi(): string {
    return `Hello, my name is ${this.name} and I build websites.`;
  }
}

const p = new Programmer("Mary");
console.log(p.sayHi());
```

Результат:

```text
Hello, my name is Mary and I build websites.
```

Оба класса содержат метод `sayHi()`, но реализации отличаются. В дочернем классе метод родителя переопределён — лектор называет это `override`.

#### Как выбирается метод

- объект `Human` вызывает собственный `Human.sayHi()`;
- объект `Programmer` вызывает собственный `Programmer.sayHi()`;
- совпадение имён не означает, что это один и тот же метод в памяти;
- если назвать методы по-разному, это будут просто два разных метода, а показанного в лекции переопределения не будет.

#### Пример среднего уровня

```ts
class Designer extends Human {
  sayHi(): string {
    return `Hello, my name is ${this.name} and I design interfaces.`;
  }
}

const human = new Human("John");
const programmer = new Programmer("Mary");
const designer = new Designer("Alex");

console.log(human.sayHi());
console.log(programmer.sayHi());
console.log(designer.sayHi());
```

Одно имя `sayHi()` имеет несколько реализаций в связанных классах.

#### В лекции изложено невнятно

Полиморфизм в этой части сводится главным образом к одинаковому имени метода в родительском и дочернем классах. Вопрос о вызове объектов через общий родительский тип здесь не рассматривается.

> **Дополнения от AI**  
> В рамках показанного примера удобно запомнить: дочерний класс переопределяет метод родителя, сохраняя его имя, а вызов выбирается по фактическому объекту. Например, `new Programmer("Mary").sayHi()` использует реализацию `Programmer`, а не `Human`.

### 6. Использование родительской реализации через `super`

Ученик спрашивает, можно ли не полностью заменять родительский метод, а использовать его результат и добавить новую информацию. Лектор отвечает, что это возможно через `super.sayHi()`.

#### Простой пример

```ts
class Programmer extends Human {
  sayHi(): string {
    return `${super.sayHi()} I build websites.`;
  }
}
```

`super.sayHi()` обращается к реализации родительского класса.

#### Пример среднего уровня

```ts
class Programmer extends Human {
  constructor(name: string, private language: string) {
    super(name);
  }

  sayHi(): string {
    return `${super.sayHi()} I write ${this.language}.`;
  }
}

const programmer = new Programmer("Mary", "TypeScript");
console.log(programmer.sayHi());
```

В лекции возможность вызова родительского метода подтверждается, но подробно не разрабатывается, поскольку, по словам лектора, в учебном проекте она использоваться почти не будет.

### 7. Параметры переопределённого метода

Во время эксперимента в `sayHi()` добавляются параметры. TypeScript выдаёт ошибку, когда сигнатура дочернего метода становится несовместимой с родительской.

Лектор формулирует следующие положения:

- при переопределении существуют правила языка, которые нужно соблюдать;
- нельзя произвольно заменить тип соответствующего параметра, например `string` на `number`;
- можно добавлять необязательные параметры;
- если параметров много, вместо длинного списка обычно передают объект;
- подробные правила совместимости в этой лекции не рассматриваются.

#### Простой пример из обсуждения

```ts
class Human {
  sayHi(message: string): string {
    return message;
  }
}

class Programmer extends Human {
  sayHi(message: string): string {
    return `${message} I build websites.`;
  }
}
```

#### Пример среднего уровня с необязательным параметром

```ts
class Human {
  sayHi(message: string): string {
    return message;
  }
}

class Programmer extends Human {
  sayHi(message: string, projectName?: string): string {
    if (projectName) {
      return `${message} I work on ${projectName}.`;
    }

    return `${message} I build websites.`;
  }
}
```

#### В лекции изложено невнятно

Код несколько раз меняется прямо во время вопросов: параметры добавляются, удаляются и становятся необязательными. Лектор сознательно не формулирует полный набор правил совместимости сигнатур, поэтому этот фрагмент нельзя использовать как завершённое объяснение темы.

> **Дополнения от AI**  
> Для текущего уровня достаточно придерживаться безопасного правила: при переопределении сохраняйте те же обязательные параметры и возвращаемый тип, что у родительского метода. Дополнительные параметры делайте необязательными. Полные правила совместимости методов — отдельная тема TypeScript.

### Быстрое повторение

```ts
abstract class Shape {
  constructor(public color: string) {}
  abstract calculateArea(): number;
}

class Rectangle extends Shape {
  constructor(
    color: string,
    private width: number,
    private height: number
  ) {
    super(color);
  }

  calculateArea(): number {
    return this.width * this.height;
  }
}

class Human {
  constructor(public name: string) {}

  sayHi(): string {
    return `Hello, my name is ${this.name} and I like travelling.`;
```

Главная мысль этой части: абстракция задаёт обязательную структуру, конкретные наследники реализуют её по-своему, а полиморфизм позволяет связанным классам использовать одинаковое имя метода с разным поведением.

## Часть 4. `protected` и интерфейсы

### 1. Полиморфизм полей

В предыдущей части полиморфизм показывался на методе `sayHi()`. В этой части лектор демонстрирует похожую идею на полях: родительский и дочерний классы используют поле с одинаковым именем и типом, но задают ему разные значения.

#### Простой пример из лекции

```ts
class Human {
  public age: number = 20;

  constructor(public name: string) {}
}

class Programmer extends Human {
  public age: number = 25;

  constructor(public name: string) {
    super(name);
  }
}
```

Объект `Human` получает `age = 20`, а объект `Programmer` — `age = 25`.

```ts
const human = new Human("John");
const programmer = new Programmer("Mary");

console.log(human.age);      // 20
console.log(programmer.age); // 25
```

#### Связь типов

Лектор подчёркивает, что классы связаны наследованием. Если родительское поле имеет тип `number`, в дочернем классе нельзя переопределить его как `string`.

```ts
class Programmer extends Human {
  // public age: string = "25"; // ошибка
}
```

#### Пример среднего уровня

```ts
class Account {
  public status: string = "basic";
}

class PremiumAccount extends Account {
  public status: string = "premium";
}

const basic = new Account();
const premium = new PremiumAccount();

console.log(basic.status);
console.log(premium.status);
```

Дочерний класс видит унаследованное поле, поэтому повторное объявление имеет смысл только тогда, когда требуется другое значение.

#### В лекции изложено невнятно

Лектор называет родительское и дочернее поля одновременно «двумя разными полями» и связанными полями, а переопределение значения — «пересозданием переменной». Модель хранения поля и точное значение термина «полиморфизм поля» подробно не объясняются.

> **Дополнения от AI**  
> Для текущей темы достаточно запомнить результат: экземпляр дочернего класса использует значение поля, объявленное в дочернем классе. Имя и совместимый тип сохраняются, а начальное значение может отличаться.

### 2. Итоговое определение ООП

По формулировке лектора, объектно-ориентированное программирование — это подход, при котором программа рассматривается как набор объектов.

Каждый объект:

- имеет собственные характеристики;
- имеет собственное поведение;
- может взаимодействовать с другими объектами;
- принимает определённые данные и выполняет действия;
- скрывает от пользователя внутренние детали реализации.

Пользователю объекта не обязательно знать, как он работает внутри. Достаточно знать, какие данные ему передать и какой результат или действие можно получить.

#### Простой пример

```ts
class Calculator {
  add(a: number, b: number): number {
    return a + b;
  }
}

const calculator = new Calculator();
console.log(calculator.add(2, 3));
```

Пользователь вызывает `add()` и получает результат, не рассматривая внутреннее устройство объекта как отдельную задачу.

#### Пример среднего уровня: взаимодействие объектов

```ts
class Printer {
  print(text: string): void {
    console.log(text);
  }
}

class Report {
  constructor(private printer: Printer) {}

  show(): void {
    this.printer.print("Monthly report");
  }
}

const printer = new Printer();
const report = new Report(printer);
report.show();
```

Здесь один объект использует другой объект. Именно такое взаимодействие отдельных объектов лектор показывает на диаграмме.

#### Четыре принципа ООП

Лектор подводит итог: ООП имеет четыре основных принципа, которые можно применять отдельно или совместно.

| Принцип | Краткий смысл по лекции |
|---|---|
| Наследование | Дочерний класс получает возможности родительского класса |
| Инкапсуляция | Внутренние поля и методы скрываются от внешнего доступа |
| Абстракция | Задаётся нужная структура и скрываются детали реализации |
| Полиморфизм | Одинаковые имена членов в связанных классах могут иметь разные реализации |

Абстракцию и полиморфизм можно использовать вместе: абстрактный метод устанавливает правило, а дочерние классы реализуют метод под тем же именем по-разному.

#### В лекции изложено невнятно

Во время обсуждения диаграммы стрелки сначала воспринимаются учениками как наследование. Лектор уточняет, что на этой диаграмме стрелки обозначают только взаимодействие объектов, но признаёт, что они могут запутывать.

> **Дополнения от AI**  
> В этой конкретной диаграмме важно не искать иерархию классов. Её смысл — показать отдельные объекты, которые могут обращаться друг к другу и использовать результаты работы друг друга.

### 3. Модификатор доступа `protected`

До этого рассматривались `public` и `private`:

- `public` — член доступен снаружи класса;
- `private` — член доступен только внутри класса, в котором объявлен.

Проблема: дочерний класс не может обратиться к `private`-полю родителя.

#### Простой пример с `private`

```ts
class User {
  private courseCount: number = 1;
}

class Student extends User {
  updateCourseCount(): number {
    // return this.courseCount = 5; // ошибка
    return 5;
  }
}
```

Чтобы сделать поле доступным наследникам, лектор заменяет `private` на `protected`.

```ts
class User {
  protected courseCount: number = 1;

  constructor() {}
}

class Student extends User {
  updateCourseCount(): number {
    return this.courseCount = 5;
  }
}
```

#### Что разрешает `protected`

- поле или метод не виден через объект снаружи;
- родительский класс имеет к нему доступ;
- дочерние классы также имеют к нему доступ.

```ts
const student = new Student();
student.updateCourseCount(); // допустимо

// student.courseCount; // ошибка: protected
```

#### Пример среднего уровня

```ts
class Employee {
  protected salary: number = 2000;
}

class Manager extends Employee {
  addBonus(amount: number): number {
    this.salary += amount;
    return this.salary;
  }
}

const manager = new Manager();
console.log(manager.addBonus(500));

// console.log(manager.salary); // снаружи недоступно
```

#### Быстрое сравнение

| Модификатор | Внутри класса | В дочернем классе | Через объект снаружи |
|---|---:|---:|---:|
| `public` | Да | Да | Да |
| `protected` | Да | Да | Нет |
| `private` | Да | Нет | Нет |

### 4. Наследование интерфейсов

Лектор возвращается к интерфейсам после изучения классов и наследования. Интерфейс может наследовать свойства другого интерфейса через `extends`.

#### Простой пример

```ts
interface User {
  name: string;
  email: string;
  age: number;
}

interface Admin extends User {
  role: "admin" | "ta" | "student";
}
```

Объект типа `Admin` обязан содержать как собственное поле `role`, так и все поля `User`.

```ts
const admin: Admin = {
  name: "John",
  email: "j@j.j",
  age: 3,
  role: "admin"
};
```

#### Наследование от нескольких интерфейсов

В отличие от класса, интерфейс TypeScript может расширять несколько интерфейсов. Имена перечисляются через запятую.

```ts
interface Contact {
  phone: string;
}

interface Dean extends User, Contact {
  department: string;
}
```

#### Пример среднего уровня

```ts
const dean: Dean = {
  name: "Anna",
  email: "anna@example.com",
  age: 40,
  phone: "123456",
  department: "Engineering"
};
```

Лектор подчёркивает, что объединять уже связанные интерфейсы иногда бессмысленно. Полезный случай — наследование от нескольких независимых интерфейсов.

#### В лекции изложено невнятно

На вопрос, почему классы не могут наследоваться сразу от нескольких классов, а интерфейсы могут расширять несколько интерфейсов, точного объяснения не даётся. Лектор предлагает отдельно изучить историю и устройство языка и отложить вопрос до review.

> **Дополнения от AI**  
> В рамках этой лекции достаточно зафиксировать правило TypeScript: класс использует один родительский класс через `extends`, а интерфейс может перечислить несколько родительских интерфейсов через запятую. Причины проектирования языка в материале не раскрыты.

### 5. Класс реализует интерфейс: `implements`

Интерфейс можно использовать не только как тип переменной, но и как обязательный шаблон для класса. Для этого применяется ключевое слово `implements`.

#### Интерфейс из лекции

```ts
interface TakePhoto {
  cameraMode: string;
  filter: string;
  zoom: number;
}
```

#### Простой пример реализации

```ts
class Instagram implements TakePhoto {
  constructor(
    public cameraMode: string,
    public filter: string,
    public zoom: number
  ) {}
}
```

Если убрать одно из обязательных свойств, TypeScript выдаст ошибку: класс заявил, что реализует `TakePhoto`, поэтому должен выполнить все правила интерфейса.

#### Пример среднего уровня

```ts
class Instagram implements TakePhoto {
  constructor(
    public cameraMode: string,
    public filter: string,
    public zoom: number
  ) {}

  showSettings(): void {
    console.log(this.cameraMode, this.filter, this.zoom);
  }
}

const photo = new Instagram("portrait", "warm", 2);
photo.showSettings();
```

Все ранее изученные правила интерфейсов продолжают действовать. По словам лектора, это относится, например, к необязательным и `readonly`-свойствам.

Интерфейс можно повторно применять к разным классам: `Instagram`, `Facebook`, `TikTok` и другим. Каждый такой класс обязан соблюдать один общий набор требований.

---

### 6. Реализация нескольких интерфейсов

Класс может реализовывать несколько интерфейсов. Их имена перечисляются после `implements` через запятую.

```ts
interface TakePhoto {
  cameraMode: string;
  filter: string;
  zoom: number;
}

interface Story {
  createStory(): void;
}

class Instagram implements TakePhoto, Story {
  constructor(
    public cameraMode: string,
    public filter: string,
    public zoom: number
  ) {}

  createStory(): void {
    console.log("");
  }
}
```

#### Простой пример

```ts
interface Named {
  name: string;
}

interface Printable {
  print(): void;
}

class Document implements Named, Printable {
  constructor(public name: string) {}

  print(): void {
    console.log(this.name);
  }
}
```

#### Пример среднего уровня

```ts
interface TakePhoto {
  cameraMode: string;
  filter: string;
  zoom: number;
}

interface Story {
  createStory(): void;
}

class SocialApp implements TakePhoto, Story {
  constructor(
    public cameraMode: string,
    public filter: string,
    public zoom: number,
    public appName: string
  ) {}

  createStory(): void {
    console.log(`Story created in ${this.appName}`);
  }
}
```

Интерфейс с методом содержит только требование к методу. Реализацию метода класс пишет самостоятельно.

#### В лекции изложено невнятно

Во время вопросов интерфейс сравнивается с абстрактным классом, а метод интерфейса — с абстрактным методом. Лектор подтверждает сходство в роли шаблона, но одновременно подчёркивает, что интерфейс и абстрактный класс — разные конструкции. Чёткое сравнение их возможностей не приводится.

> **Дополнения от AI**  
> Для повторения текущей лекции можно провести только ограниченную параллель: и интерфейс, и абстрактный класс способны устанавливать требования к будущей реализации. Но в TypeScript это разные механизмы и используются разным синтаксисом: класс `extends` другой класс, а интерфейс класс `implements`.

### 7. Как выбирать способ решения

В конце занятия лектор объясняет, что одну задачу обычно можно решить несколькими способами. На начальном этапе главное — получить правильный результат.

После этого решения можно сравнивать по дополнительным критериям:

- скорость выполнения;
- количество кода;
- удобство для пользователя;
- простота поддержки;
- лёгкость будущих изменений;
- объём требуемых усилий.

#### Простой пример

```ts
const result = 2 + 2;
```

Если задача требует получить `4`, результат должен быть именно `4`, независимо от выбранной структуры кода.

#### Пример среднего уровня

Вместо повторения одной логики в нескольких местах можно вынести её в класс и повторно использовать:

```ts
class PriceCalculator {
  addTax(price: number): number {
    return price * 1.1;
  }
}

const calculator = new PriceCalculator();

console.log(calculator.addTax(100));
console.log(calculator.addTax(250));
console.log(calculator.addTax(500));
```

По лекции ООП помогает:

- не переписывать уже существующий код;
- использовать класс, не зная всех деталей его реализации;
- изолировать имена и внутренние данные внутри объектов;
- создавать и применять библиотеки и фреймворки.

Домашняя работа должна дать практику выбора: определить, какой принцип ООП подходит для конкретной задачи. В дальнейшем принципы будут применяться в учебном проекте.

#### В лекции изложено невнятно

Сначала звучит утверждение: «если работает, то нормально», затем лектор уточняет, что решения отличаются производительностью, длиной, удобством и поддерживаемостью. Граница между просто работающим и качественным решением формулируется постепенно.

> **Дополнения от AI**  
> Удобная последовательность оценки: сначала проверить правильность результата, затем сравнить рабочие варианты по читаемости, скорости, повторному использованию и удобству будущих изменений. Этот порядок соответствует критериям, перечисленным лектором.

# Ответы на вопросы

3. Готовый объект можно использовать по его доступным возможностям, не всегда зная его внутреннее устройство.
4. Создание класса на основе другого класса с получением его полей и методов.
5. Родительский класс и дочерний класс.
6. Класс `Color` наследуется от класса `Car`.
7. Чтобы передать `name` конструктору родительского класса `Car`.

9. Да. В лекции `Color` и `Model` отдельно наследуются от `Car`.
10. Нет. Эти классы находятся на одном уровне и не наследуются друг от друга.
11. Собственные элементы `Type`, доступные элементы `Model` и доступные элементы `Car`.
12. Нет. Родительский класс не получает элементы дочернего класса.
13. Нет. По правилу из лекции у класса может быть только один непосредственный родитель.
14. Значения должны соответствовать параметрам родительского конструктора в ожидаемом порядке.
15. Способность класса или объекта определять, какую информацию открыть внешнему коду, а какую скрыть.
16. Внешний код видит метод расчёта зарплаты и может напрямую изменить публичный `monthlyBonus`.
